## 三、⚠️ 唯一待澄清项：`blog_plugins.kind` 跨壳语义冲突（→ REQ-004）

**同一列、同一 manifest 字段，两壳取值语义完全不同：**

| | 取值域 | 含义 | 消费方 |
|---|---|---|---|
| **AiKlog（本壳）** | `plugin` \| `theme` | **应用中心安装类型分类**（区分插件/主题目录与卸载路径） | `apps_market.go` 全链路、`blog_plugins` 列表渲染 |
| **上游 v2** | `ui` \| `capacity` | **能力插件协议层分类**（有无后端入口） | `validatePluginV2` |

本壳 DDL：`kind TEXT NOT NULL DEFAULT 'plugin'`；你方 DDL：`kind TEXT NOT NULL DEFAULT 'ui'`。
**若直接按 v2 语义覆盖，本壳应用中心的插件/主题分类判定会全线失效**（存量数据 + 安装/卸载/列表全部受影响）。

**我方倾向的三种解法（请上游择一确认）：**

- **A（推荐）**：`kind` 保持本壳 `plugin|theme` 语义不动，v2 的能力分类**另起一列**（如 `capability_mode`）承接 `ui|capacity`；
- **B**：`kind` 收敛为 `ui|capacity`，本壳应用中心的插件/主题分类上提到**包 manifest 的 `type` 字段**（`apps_market` 侧改造 + 存量数据迁移）；
- **C**：`kind` 做**联合取值**（`plugin-ui` / `plugin-capacity` / `theme-ui` …），一个字段承载两维，但需双方约定解析器。

> 该冲突**不构成缺件**，故本轮三单照常关闭；澄清结果只影响合入方式，不影响 `validatePluginV2` 的其余校验。
