# 主题上架操作规范（AiKlog 壳）

> 适用范围：AiKlog（爱库录）博客壳的主题上架。给 **Klog 方（壳运营/平台方）** 的操作规范。
> 核心模型：**第三方交付 zip → Klog 审核 → 构建接入（一次性）→ 市场上架 → 用户安装/切换（运行时，零编译）**。
> 底层实现：主系统 `server/internal/handler/blog_market.go`（zip 下载 + SHA-256 + manifest 校验 + frontend_entry 一致性）+ AiKlog 前端 `web/src/themes/index.js`（主题注册表）。

---

## 一、总体流程

```
第三方                      Klog 方（平台）                     最终用户
─────────                ──────────────                    ──────────
交付 zip 源码包  ──▶  ① 审核（安全/协议/质量）
                      ② 构建接入：主题注册进 AiKlog 前端
                         themes/index.js + 后端 frontend_entry
                      ③ 市场上架：包托管 + index.json 条目
                                                            ──▶ 市场中心可见
                                                            ──▶ 点「安装」→ 服务端校验 → 注册生效
                                                            ──▶ 博客设置/左上角切换 → 运行时生效
```

- **「构建接入」只发生在 Klog 方，且每个新主题只做一次**。
- 用户端全程无编译动作：安装/切换/卸载都是前端运行时操作。
- 顺序不可反：**先构建接入、后上架**。服务端的 `frontend_entry` 一致性校验会强制这一点（组件未注册 → 安装被拒）。

### 版本演进规则（完整交付铁律）

- **一个主题 = 一个 manifest = 一个完整包 = 一个版本号**。宿主侧每个主题版本都要重新编译嵌入 + 上架托管，因此任何增量功能（哪怕只改一个组件）都必须 **bump version 后整包重发、重走审核与构建接入**。
- **不存在「补丁包 / 增量包 / 分期交付」形态**：市场与注册表只认完整包，分批交付会导致编译产物与包版本错位，上架即乱。
- 同一主题多版本并存时，市场条目指向最新完整包；旧版本下架由 Klog 方在市场索引操作，与主题方无关。

## 二、第三方交付格式（zip 源码包）

### 包结构

```
aiklog-theme-<id>-<version>.zip
├── manifest.json          # 必填
├── src/ 或 dist/          # 主题组件（Vue SFC / 编译产物）
│   └── ...                # entry 组件 + 页面组件（post/tag/category/archive/search）
├── preview/               # 上架预览材料（v1.4 起全部必需，见规范 §0.4）
│   ├── cover.png          # 市场卡片封面 1200×750（8:5）≤500KB（PNG/JPG/WebP 均可）
│   ├── demo.html          # 静态样板演示页（单文件自包含，≤512KB，无脚本/远程请求）
│   └── full-*.png         # 整页实机截图 ≥2 张：列表页+文章页（≤1MB/张，png≤2MB，建议补内页/移动端）
├── README.md              # 必需：主题介绍（固定小节：简介/设计理念/版式特点/适用场景/作者与支持）
└── LICENSE                # 可选
```

> **上架材料审核点（v1.4）**：`preview/` 三类材料 + 包根 `README.md` 主题介绍均为**必需**，缺任一即退回补正；截图视觉须与实机一致（与 `?theme=<id>` 渲染对照），demo.html 同理。市场卡片展示封面图、详情页嵌入 `demo.html` 与介绍文案，依赖宿主侧市场接口扩展（index.json 条目 `cover` / `preview` / `intro` 字段 + 前端卡片渲染）——宿主支撑上线前，材料仍必须随包交付（单包原则）。

### manifest.json（对照主系统 pluginManifest）

```json
{
  "id": "theme-clean",
  "kind": "theme",
  "name": "素简",
  "version": "1.0.0",
  "description": "极简风博客主题",
  "author": "第三方团队",
  "min_core_version": "0.1.0",
  "frontend_entry": "theme-clean"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，kebab-case；**等于 frontend_entry 与注册表键** |
| `kind` | 是 | `theme`（区别于 `plugin`/`capacity`） |
| `name` / `version` / `description` / `author` | 是 | 展示信息；version 用 semver |
| `min_core_version` | 是 | 低于内核版本 → 安装被拒（409） |
| `frontend_entry` | 是 | **必须命中已注册的前端组件**，否则安装报「前端组件未在主系统注册」 |
| `mount_points` | 否 | 主题一般不填（挂载点属功能插件）；填了按博客插件语义生效 |

## 三、Klog 方审核清单

逐项通过才能进入构建接入：

1. **安全**
   - 无 `eval` / 动态执行远程代码 / 外链脚本（除主题声明的 CDN 资源白名单）；
   - 无硬编码密钥、令牌、个人信息；无路径穿越（zip slip）、无越权 API 调用；
   - 数据边界：`dataScope` 默认 `shared`（只展示已分享文件）；声明 `library`（直读文件库）的主题**仅限内网/单机自用**，不得对外公开上架。
2. **协议合规**
   - manifest 完整、id 全局唯一、版本语义化；
   - `frontend_entry` 与主题 id 一致（注册表键 = manifest id）；
   - 页面契约（`entries`）：明确声明接管 list/post/tag/category/archive/search 哪些页；未声明的页面由宿主默认渲染 + 主题 tokens 兜底（至少配色/字体一致）。
3. **样式隔离**
   - Vue scoped style 或类名前缀；设计令牌统一 `--th-*` 前缀，不污染主应用；
   - 移动端可读、无横向溢出。
4. **质量**
   - 空态/加载态/错误态有展示；单项主题抛错不影响主应用与其它主题（注册处已 try-catch 隔离）；
   - 预览图、README、版权声明齐全。

## 四、构建接入（Klog 方，一次性）

1. **AiKlog 前端注册**：把主题组件放入 `web/src/themes/` 下，在 `web/src/themes/index.js` 调 `registerTheme({...})`：

   ```js
   registerTheme({
     id: 'theme-clean',          // = manifest.id = frontend_entry
     title: '素简',
     desc: '极简风博客主题',
     version: '1.0.0',
     entry: ThemeCleanEntry,     // 列表页入口组件
     pages: ['posts'],           // 主题提供的页面
     entries: {                  // 页面级入口，未声明走宿主默认页
       post: ThemeCleanPost,
       tag: ThemeCleanTag,
       // category / archive / search ...
     },
     tokens: { /* --th-* 设计令牌说明 */ },
     dataSources: ['blog'],      // 'blog'（通用，推荐）| 'collect'（采集视图特例）
     dataScope: 'shared',        // shared（默认）| library（仅内网自用）
   })
   ```

2. **后端 frontend_entry 注册**：把 `id` 加入服务端内置注册表（主系统 `server/internal/handler/blog_plugins.go` 的 `builtinFrontendEntries`；AiKlog 独立后端同样维护）——否则用户市场安装时会被 `frontend_entry` 一致性校验拒绝。

3. **构建上线**：重新构建前端产物并发布（`?cb=` 强刷验证主题可见、可切换）。

> 后端 `builtinFrontendEntries` 当前仅含内置 `blog-meta-footer`，**每个新主题接入都必须同步注册**，这是当前机制下「先构建后上架」的强制闸门。

## 五、市场上架（Klog 方）

1. **打包**：`aiklog-theme-<id>-<version>.zip`（含 manifest.json），计算 `sha256`。
2. **托管**：zip 放市场包服务器（`aikmap.cn/market/official/` 统一索引源，或壳自身 `/market/official/` 目录），保证可下载。
3. **索引**：在 `index.json` 的 `themes[]` 增加条目：

   ```json
   {
     "id": "theme-clean",
     "name": "素简",
     "version": "1.0.0",
     "download_url": "https://aikmap.cn/market/official/themes/theme-clean-1.0.0.zip",
     "sha256": "<zip 的 sha256 十六进制>",
     "target": ["aiklog", "aikmap"],  // 适用壳清单（壳ID：aiklog/aikbox/aikdex/aikmap）；空=兼容所有壳。博客主题建议含 aikmap（主系统自带博客面），写死单壳会导致其他壳 422 装不上
     "tier": "free",                // free | paid（付费需 pro license，预留）
     "price": "",                   // 展示价
     "free_until": ""               // 限免截止 YYYY-MM-DD（预留）
   }
   ```

4. **上架验证**：市场接口 `GET /api/v1/blog/market` 能看到该主题（applicable=true）；走一遍安装流程通过。

## 六、用户侧（最终用户，零编译）

1. **市场中心** → 主题 tab → 看到主题卡片（名称/描述/版本/作者）。
2. 点 **安装** → 后端 `POST /api/v1/blog/market/install {id}`：
   下载 zip → SHA-256 校验 → 解包校验 manifest（id/版本/frontend_entry）→ 写入 `blog_plugins`（enabled=true）→ 返回成功。
3. 博客公开页 **左上角切换器 / 博客设置** 切换该主题 → **运行时立即生效**（localStorage + 服务端权威值双轨；用户手动选择本地优先）。
4. **卸载** = 删除登记，挂载点组件消失，不残留。

> 安装/切换/卸载都不触发任何编译或服务重启。

---

## 七、版本升级 / 下架

- **升级**：交付新版 zip（版本号递增）→ 审核 → 若组件无结构性变更仅替换包与索引条目；若组件变更需重新构建接入一次 → 更新 `index.json` 的 download_url/sha256/version。已安装实例安装状态保留，`blog_plugins` 的 manifest 由安装方按需更新。
- **下架**：从 `index.json` 移除条目 → 市场不再展示；已安装用户**保留可用**（可继续切换），需要时平台可远程禁用（`toggle enable=0`）。
- **改名/改 id**：视为新主题，旧 id 走下架，避免「安装后 registry 对不上」的悬挂状态。

## 八、现状与差距（诚实记录）

| 能力 | 状态 |
|---|---|
| 市场安装管线（zip+sha256+manifest+frontend_entry 校验） | ✅ 主系统已实现 |
| 主题运行时切换（无需重编译） | ✅ AiKlog 前端已实现 |
| 主题组件随 zip 同包注入、前端动态加载 | ❌ 未实现（AiKlog PLUGIN-MARKET v0.1 目标态）——当前主题必须编译进前端产物 |
| 付费/tier 门禁 | 🟡 已预留（pro license 校验），定价策略待定 |
| 服务端「远程禁用/下架」 | ✅ 已实现（toggle） |

**含义**：当前「用户安装」是**登记 + 启用**，渲染依赖**已随壳构建发布的主题组件**。所以 Klog 方上架节奏 = 「每批主题 → 审核 → 构建接入 → 上架」，市场才能保持「装即用」体验。若要支持「纯 zip 远程安装即用」（无需构建发版），需要补「前端远程组件加载」能力——属后续迭代项，可在主题协议 v2 一并规划。
